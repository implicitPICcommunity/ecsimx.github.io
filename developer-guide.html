Developer Guide

Structure, GPU porting notes, and validation guidance for working on ECsim-X while preserving its energy-conserving numerics.

Code architecture

AreaAs described in the papers
FieldsFields class: E on nodes, B on nodes and cell centres, implicit current, mass matrices (4D array)
ParticlesParticles class per species; seven 1D arrays (x, y, z, u, v, w, q)
Particle moverupdateVelocity, updatePosition, fixPosition (GPU)
MomentscomputeMoments: Ĵ and 14 mass matrices (GPU)
DiagnosticscomputeCharge, computeCurrent (GPU)
Field solverPETSc matrix-free GMRES (CPU, MPI)
Parallel layerCartesian MPI decomposition; particle exchange via MPI_Sendrecv; one rank per GPU

GPU development notes

  • Per-particle loops are independent: #pragma acc parallel loop.
  • Deposition into shared grid nodes uses #pragma acc atomic update; array reductions were abandoned due to compiler limitations.
  • Flatten multi-dimensional arrays and replace small matrices with scalars to reduce pointer chasing and register use.
  • Do not fully unroll the mass-matrix loops; it increased register pressure.
  • Use managed memory with cudaMemPrefetchAsync rather than deep-copying nested structures.
  • Profile with Nsight Systems for transfers and page faults; end-to-end timing matters as much as kernel time.

Numerical correctness and energy conservation

Any change must preserve the discrete scheme that gives exact energy balance at θ = ½.

  • Track kinetic, electric, and magnetic energy under a fixed solver tolerance.
  • Validate against 1D/2D two-stream and current-filamentation runs; the published CPU and GPU curves overlap.
  • Expect round-off differences from atomic accumulation order. Separate them from systematic drift with repeated runs.
  • Do not claim bitwise CPU/GPU equivalence.

Contribution workflow

Until a project policy is published, the following generic workflow applies; see Contribute.

Issue

Describe the bug or feature and the acceptance criteria.

Implementation

Make a focused change and explain numerical and performance implications.

Testing

Run validation, record energy diagnostics and benchmark evidence.

Review

Summarize results, limitations, and documentation updates.

Roadmap stated in the papers

  • A pure CUDA implementation (under development).
  • Faster I/O and better CPU–GPU overlap.
  • Offloading more routines, such as the field solver and initialisation, to cut time and energy.
  • Reducing field-solver communication, the main scaling limit on CPUs and at large GPU counts.

For user-level setup, see Documentation.
